# c9n 0.9.6

The weekly overview, day navigation, GPU work and overview of waiting human decisions have been brought together in one version.

## Improvements

Under “Today”, the weekly overview shows confirmed completions by calendar day, including the existing Hub history. Selecting a day opens that day's tasks. The selected day is retained during search, reload and back/forward navigation. Future days and missing data are marked as unknown. Task counts are not converted into estimated working hours or savings.

The GPU overview links the displayed work to the actual tasks and model calls. It shows duration and the data timestamp and refreshes regularly. If reading fails, the last read state remains visible with a clear message and an option to retry. Running tasks and occupied model-call slots are counted separately. If a slot is occupied but its task association is missing, this is shown explicitly. Up to ten recently completed, associated calls per pool show the available history with result, timestamp and task link. This does not measure GPU utilisation as a percentage; a completed model call does not mean the task is complete.

The human-decision overview shows the responsibility actually recorded and the reason feedback is needed. Waiting time is calculated only from a confirmed start of the current decision round. If that timestamp is missing, it remains unknown; the age of the entire task is not presented as the waiting time of that round.

Tasks initially open for reading. Editing is an explicit action. A slow opening can be cancelled; after 20 seconds, it can be retried. “Reviewstand prüfen” (check review status) reads Jira and public GitHub pull requests without granting approval. Person and process filters are retained on reload and when navigating back. The table of times can be scrolled sideways on small screens. Historical comments count as answered only when a human response in the same waiting round is confirmed.

Providers for AI and GPU connections can be configured and checked under “Settings”. Saved settings and the connection state actually checked remain distinct. Your own GPU on the network can be connected through an Ollama or OpenAI-compatible model server. An API key is optional for your own server. The “All pools” selection includes the configured connections. For the Melious connection carried over into c9n, setup shows the pool limit actually applied. Saving access details alone does not confirm a successful model call or a provider's pricing plan.

The task list distinguishes waiting for a slot, running work, human feedback, other blocks and completed tasks. Editable waiting cards can be reordered by dragging or using the reorder buttons. Background refreshes keep the cards in place and their actions usable. Navigation and the actor view are more compact; loading indicators show data that is still pending.

The existing knowledge area is integrated: folders, files, overview and search are read through each person's OpenViking connection. If the knowledge service is configured for automatic setup, c9n creates personal access for each person. An existing personal key can still be used; stored access credentials are encrypted. Under “Mit Claude verbinden” (connect to Claude), you can reveal your personal connection details after explicit confirmation, copy them, and hide them again. Administrators can set the knowledge service's public address in the interface for this purpose. The interface distinguishes automatically created access from access entered manually.

Tasks link to their associated Hermes sessions. New messages can appear automatically in an open session; automatic refresh can be switched off. Recently saved messages indicate session activity and do not, by themselves, establish that a task is running. Session matching checks a limited set of sessions for the current agent assignment and the default profile; older sessions may be missing. If reading fails, the last state for the same task remains visible.

Administrators can use “Gespräch” (conversation) to write directly to a Hermes helper, read replies, view tool output and interrupt a response. Confirmations and follow-up questions requested by the profile can be answered there. A finished session can be resumed; open sessions remain protected even if they have not sent a message for some time. The chat connection starts together with agent execution in the c9n image. The profile determines which tools require confirmation; the chat window does not enforce an additional approval for every tool action. Conversations are initially available in the primary workspace.

The existing agent settings are regularly synchronised with the built-in execution environment. The scan profile finds its existing working instructions after migration. All c9n services use the same versioned c9n image.

## Limitations

Missing completeness information for the completion history is shown explicitly. Weekly counts represent the evidenced data state and can change with new completions. They do not establish a complete historical analysis.

The review check supports public GitHub pull requests. Separate access for private pull requests has not yet been configured. Automatic continuation after human approval has not yet been verified. The time spent in a Jira status and the age of the current assignment do not, by themselves, establish when the current content review round began.

The knowledge area requires valid personal access credentials. Automatic setup requires the knowledge service to be configured accordingly. Reading and searching with real user data have not been publicly verified in this release. Writing, creating new resources, and managing skills or permissions are not yet included in this knowledge area.

The full transfer and functional acceptance of all existing Hub processes remain unfinished. Real agent work and a prepared delivery do not replace human approval or confirmed publication. Existing tasks may still require specific feedback or clarification of a block.

A manually started agent task can run with its assigned agent. The intended start path for a newly created graphical process has not yet been fully verified. Full automatic routing of all graphical steps and the connection of new Bruno schedules are still not configured. Active existing schedules do not establish this new connection. Kalle's code is checked statically and is not executed during that check.

Creating or saving a task does not start it. Execution requires a working model connection and valid access to the services being used. This version does not establish full customer acceptance or general production readiness. The installation package supports Linux on amd64.
